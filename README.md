# Yourself — ملفات جذرية بلا مكتبات واجهة

كل ما تحتاجه لرفع واجهة الموقع موجود في الجذر بأربعة ملفات: `index.html` و`style.css` و`script.js` و`config.js`. انسخ هذه الملفات الأربعة إلى مجلد الموقع نفسه. `supabase.sql` ملف واحد تشغّله في SQL Editor، و`delete-account.ts` وظيفة اختيارية تنشرها منفصلة عبر Supabase CLI، و`README.md` دليل. تستخدم الواجهة HTML وCSS وJavaScript وFetch المدمجة في المتصفح، بلا npm أو SDK أو مكتبات واجهة أو مجلدات فرعية.

## تشغيل الموقع

ارفع ملفات الواجهة الأربعة فقط إلى مجلد الموقع نفسه على استضافة تدعم HTTPS. لا ترفع ملف SQL أو ملف الوظيفة الخادمية كملفات عامة. لا تفتح `index.html` عبر `file://`، لأن تسجيل الدخول وطلبات Supabase تحتاج أصل ويب. للتجربة المحلية شغّل `python3 -m http.server 8080` داخل المجلد وافتح `http://localhost:8080`.

## إعداد Supabase

1. تم إعداد `config.js` بالرابط العام لمشروع Supabase `jxdzihloouksaebxigrz` والمفتاح **Publishable** الذي زودتني به. هذا المفتاح مصمم للاستخدام في واجهة عامة؛ حماية البيانات تعتمد على سياسات RLS. لا تضف `service_role` أو أي مفتاح سري إلى ملفات الموقع.
2. شغّل `supabase.sql` كاملًا في **SQL Editor** أولًا؛ فهو ينشئ الجداول وسياسات الحماية والمشغّل الذي يسجل الحسابات الجديدة كـ`pending`.
3. فعّل **Allow new users to sign up** للسماح بالتسجيل من الموقع. في **Authentication → Providers → Email** إعداد **Confirm email** يتحكم بتأكيد البريد؛ لا أغيّر إعدادات Auth الحية من هذه النسخة. لا تمنح دور المطور لحساب قبل التأكد أنه حسابك.
4. سجّل من صفحة إنشاء الحساب في الموقع بالبريد المحدد للمطور: `Haider@gmail.com` أو `Huang@gmail.com`. سيظهر الحساب مؤقتًا بانتظار الموافقة. بعدها شغّل `developer-bootstrap.sql` في **SQL Editor**؛ سيوافق على هذين البريدين المحددين ويمنحهما دور المطور، ولن يفعّل المستخدمين الآخرين. تأكد من ظهور `READY: developer can sign in` للبريد الذي سجّلت به.
5. بعد ظهور `READY`، أعد تحميل الموقع أو سجّل الدخول مجددًا. إذا كان تأكيد البريد مطلوبًا وحساب Auth غير مؤكّد، أكّد البريد من **Authentication → Users**؛ SQL لا يؤكد البريد ولا يغيّر كلمات المرور. لا تعدّل `auth.users` مباشرة.
6. اترك التسجيل العام مفتوحًا إذا أردت استقبال مستخدمين؛ سيظلون بحالة `pending` إلى أن يوافق مطور من لوحة المطور. لا يوجد تسجيل دخول Google. إيقاف **Confirm email** يسمح لأي شخص بالتسجيل بعنوان بريد لا يملكه، لذا لا تمنح دور المطور تلقائيًا بمجرد مطابقة البريد.
7. لا تحتاج أوامر `supabase login/init/link` لتشغيل SQL من لوحة التحكم. في **Authentication → URL Configuration** أضف رابط الموقع الفعلي إلى **Site URL** و**Redirect URLs**. رابط استعادة كلمة المرور يستخدم PKCE، لذا افتحه في المتصفح والجهاز نفسيهما اللذين طلبا الاستعادة.

### تفعيل المطور لأول مرة

الحسابات العادية الجديدة تبقى `pending` وتنتظر موافقة المطور. لحساب المطور الأول، سجّل بالبريد المحدد ثم شغّل `developer-bootstrap.sql` بنفسك من لوحة SQL التي تملكها؛ لا تنتظر موافقة مطور آخر. بعد ظهور `READY`، أعد تحميل الموقع وسجّل الدخول. لا تضع كلمات المرور داخل SQL أو ملفات الواجهة، ولا تمنح دور المطور تلقائيًا لمجرد أن البريد يطابق اسمًا مسموحًا.

### مراجعة RLS في مشروع موجود

قبل استخدام المشروع، راجع السياسات القديمة؛ سياسات PostgreSQL permissive تُجمع بمنطق OR، وقد تُبقي سياسة مخصصة قديمة وصولًا واسعًا. الملف يعيد إنشاء السياسات التي يملكها باسمها، لكنه لا يخمن أسماء السياسات المخصصة الأخرى. استعلم عن السياسات من SQL Editor:

```sql
select schemaname, tablename, policyname, permissive, roles, cmd, qual, with_check
from pg_policies
where schemaname in ('public', 'storage')
order by schemaname, tablename, policyname;
```

احذف أو ضيّق السياسات القديمة فقط بعد التحقق من عدم الحاجة إليها. تم التحقق من اتصال قراءة فقط إلى Auth Settings؛ لم يُنفذ SQL على قاعدة البيانات الحية أو يجرّب تسجيل الدخول.

## الدعم والإشعارات

المستخدم يفتح محادثة خاصة به، ويستطيع المطورون رؤيتها والرد عليها وإغلاقها أو إعادة فتحها. تمنع قاعدة البيانات صاحب الحساب من إرسال رسالة جديدة بعد إغلاق المحادثة. الإشعارات التي يرسلها المطورون تظهر داخل التطبيق فقط. لا يوجد مزود بريد مربوط؛ إرسال البريد الفعلي يحتاج اختيار مزود ووظيفة خادمية، وتخزين مفتاح المزود في **Edge Function Secrets**، لا في `config.js` أو SQL أو واجهة المتصفح.

## الصور وحذف الحساب

تُرفع الصورة إلى حاوية `avatars` الخاصة في Supabase Storage، مع قصرها على الصور المدعومة وبحد أقصى 2 ميجابايت. لحذف الحساب، انسخ `delete-account.ts` إلى مسار Supabase CLI القياسي `supabase/functions/delete-account/index.ts` ثم انشره بـ `supabase functions deploy delete-account`. هذا الجزء فقط يحتاج مجلد وظيفة عند النشر؛ بقية ملفات الموقع تظل في الجذر. لا يسمح المسار لمطور بحذف حساب مطور آخر، وتغيير حالة اعتماد حساب المطور محظور؛ يظل حذف الحساب الذاتي ممكنًا. خزّن `SUPABASE_SERVICE_ROLE_KEY` في **Edge Function Secrets** فقط. لا تتضمن النسخة المحلية بيانات هذا المفتاح ولا يمكن حذف الحساب فعليًا قبل نشر الوظيفة.

## حساب الدخل

تحوّل الحاسبة الراتب الشهري إلى قيمة ساعة وفق `52 ÷ 12` أسبوعًا بالشهر، وأيام العمل وساعات الجدول المسجل. تُحفظ التقديرات اليومية المكتملة تلقائيًا عند الانتقال إلى يوم جديد وتُستعاد الأيام التي فاتت أثناء عدم فتح الموقع ابتداءً من آخر تاريخ مزامنة. لا تُنشأ تقديرات تاريخية قبل تهيئة تاريخ الأساس لتجنب اختلاق دخل سابق. جلسات العمل اليدوية تُقسّم عبر تواريخها عند تجاوز منتصف الليل. هذه أرقام تقديرية وفق جدول العمل، وليست كشوف رواتب أو إثبات حضور أو دفعات.

## حدود بيانات الاتصال والأمان

رابط PostgreSQL الذي يتضمن `[YOUR-DATABASE-PASSWORD]` قالب ناقص، وليس مفتاحًا صالحًا أو مطلوبًا للواجهة أو لتشغيل SQL عبر Dashboard. الرابط والمفتاح العام Publishable المتاحان موجودان في `config.js`. لا تستبدل القالب بكلمة مرور داخل ملفات الموقع؛ أي زائر يستطيع قراءة ملفات الواجهة. عند الحاجة إلى Supabase CLI، أدخل كلمة المرور عند الطلب في بيئة محلية موثوقة ولا تحفظها في المستودع أو ملفات الواجهة. لا تضع مفتاح `service_role` أو أسرار البريد في أي ملف عام.

كلمات المرور التي أُرسلت سابقًا في المحادثة تُعد مكشوفة؛ لا تستخدمها وأعد تعيينها إن استُخدمت. اختر كلمات مرور فريدة وقوية للحسابين.

## تحديث Yourself — إصدار التصميم والإشعارات

يتضمن هذا الإصدار نظام مظهر جديدًا بأربعة اختيارات (الغابة والليل والمحيط والرمال)، تخطيطًا متجاوبًا، قائمة تنقل جانبية ثابتة على الشاشات الواسعة وقابلة للفتح على الهاتف، تحسينات لنموذج الدخول والحقول والأزرار، بطاقة ملف شخصي وصورة دائرية أوضح، ولوحة حاسبة موزونة بأزرار متساوية مع زر نتيجة بعرض الصف. اختيار صورة المستخدم ما زال يرفع الصورة إلى حاوية Supabase الخاصة بعد التحقق من النوع والحجم.

### تحديث مشروع قائم

1. احتفظ بنسخة احتياطية من الملفات الحالية.
2. ارفع `index.html` و`style.css` و`script.js` و`config.js` الجديدة إلى مجلد الموقع نفسه.
3. افتح Supabase Dashboard ثم **SQL Editor** وشغّل `migration_notifications.sql` مرة واحدة. لا تضع هذا الملف داخل المجلد العام للموقع.
4. أعد تحميل الموقع تحميلًا كاملًا، ثم سجّل الدخول بحساب مطوّر.
5. اختبر طلب تسجيل جديد تجريبيًا: ينبغي أن يظهر إشعار «طلب تسجيل جديد» في صندوق الوارد داخل التطبيق لكل مستخدم لديه دور `developer`، وتظهر نتيجة المراجعة في حساب صاحب الطلب.

لإنشاء مشروع جديد من الصفر، استخدم `supabase.sql` المحدّث بدل تشغيل ملف الترحيل فقط. لا تشغّل `developer-bootstrap.sql` إلا وفق تعليمات تهيئة المطوّر أعلاه وبعد التأكد من الحسابات المقصودة.

### ما الذي يفعله نظام الإشعارات؟

- يستطيع المطوّر إرسال إشعار لمستخدم واحد أو لكل المستخدمين أو لكل المطورين.
- عند إنشاء حساب جديد، ترسل قاعدة البيانات إشعارًا داخل التطبيق إلى كل حساب يحمل دور `developer`؛ لا يعتمد ذلك على فتح لوحة المطوّر لحظة التسجيل.
- عند قبول الطلب أو رفضه، يصل لصاحب الطلب إشعار داخل التطبيق.
- تظهر أعداد الإشعارات غير المقروءة في شريط التطبيق وتتحدث دوريًا أثناء تسجيل الدخول.
- هذا صندوق وارد داخل الموقع، وليس إشعار هاتف فوريًا ولا رسالة بريد إلكتروني. البريد أو Push يحتاجان مزود إرسال ووظيفة خادمية وأسرارًا محفوظة في Supabase Edge Function Secrets.

### حفظ الدخل على المدى الطويل

يُحفظ سجل الدخل اليومي في `user_data.payload` في Supabase ويُستعاد تلقائيًا عند الدخول. أزيل الحد البرمجي السابق البالغ عشر سنوات؛ تُستعاد الفترات الفائتة على دفعات سنوية صغيرة، ويحفظ كل جزء بنجاح قبل متابعة الجزء التالي، مع تقريب المبالغ إلى منزلتين عشريتين لتقليل أخطاء الكسور. لا تُكتب قيمة يوم سبق تسجيله مرة أخرى. هذه المبالغ تظل تقديرات مبنية على جدول العمل والراتب الذي أدخله المستخدم، وليست تحويلات أموال أو رصيدًا بنكيًا حقيقيًا. احتفظ بنسخة احتياطية دورية من قاعدة بيانات Supabase كخطة حماية إضافية.

### الاختبارات وحدود التحقق

يوجد اختبار عقد للمحلّل الحسابي، وترتيب الآلة الحاسبة، واستهداف الإشعارات، ومشغّل طلبات التسجيل، واسترجاع الدخل، واختيارات المظهر. شغّله من داخل مجلد المشروع باستخدام `node --test tests/source-contracts.test.cjs`. يجب نشر الملفات وتشغيل SQL على مشروع Supabase الفعلي قبل اختبار تسجيل الدخول، رفع الصور، وصول الإشعارات، أو استمرار البيانات على حساب حقيقي؛ هذه العمليات لا يمكن تأكيدها من نسخة محلية لا تملك صلاحية إدارة قاعدة البيانات الحية.
