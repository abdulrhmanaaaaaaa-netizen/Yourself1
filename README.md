# Yourself — ملفات جذرية بلا مكتبات واجهة

كل ما تحتاجه لرفع واجهة الموقع موجود في الجذر بأربعة ملفات: `index.html` و`style.css` و`script.js` و`config.js`. انسخ هذه الملفات الأربعة إلى مجلد الموقع نفسه. `supabase.sql` ملف واحد تشغّله في SQL Editor، و`delete-account.ts` وظيفة اختيارية تنشرها منفصلة عبر Supabase CLI، و`README.md` دليل. تستخدم الواجهة HTML وCSS وJavaScript وFetch المدمجة في المتصفح، بلا npm أو SDK أو مكتبات واجهة أو مجلدات فرعية.

## تشغيل الموقع

ارفع ملفات الواجهة الأربعة فقط إلى مجلد الموقع نفسه على استضافة تدعم HTTPS. لا ترفع ملف SQL أو ملف الوظيفة الخادمية كملفات عامة. لا تفتح `index.html` عبر `file://`، لأن تسجيل الدخول وطلبات Supabase تحتاج أصل ويب. للتجربة المحلية شغّل `python3 -m http.server 8080` داخل المجلد وافتح `http://localhost:8080`.

## إعداد Supabase

1. تم إعداد `config.js` بالرابط العام لمشروع Supabase `jxdzihloouksaebxigrz` والمفتاح **Publishable** الذي زودتني به. هذا المفتاح مصمم للاستخدام في واجهة عامة؛ حماية البيانات تعتمد على سياسات RLS. لا تضف `service_role` أو أي مفتاح سري إلى ملفات الموقع.
2. إعداد المشروع الحالي يسمح بالتسجيل العام (`disable_signup=false`)، لذا أوقف مؤقتًا خيار **Allow new users to sign up** في إعدادات Auth قبل إعداد حسابي المطورين. هذا يمنع حجز بريديهما أثناء التحضير.
3. في **Authentication → Providers → Email** أوقف خيار **Confirm email**. لا أغيّر إعدادات المشروع الحية من هذه النسخة. افحص **Authentication → Users** واحذف أي حساب غير موثوق يستخدم بريدي المطورين قبل المتابعة.
4. أنشئ `Haider@gmail.com` و`Huang@gmail.com` من **Authentication → Users** بكلمتي مرور قويتين وفريدتين. لا تضع كلمات المرور في SQL أو ملفات المشروع؛ SQL لا ينشئ مستخدمي Auth ولا يحدد كلمات المرور. بعد ذلك انسخ محتوى `supabase.sql` كاملًا إلى **SQL Editor** وشغّله كوحدة واحدة. يجمع الملف جزأي SQL المرفقين ويضيف جداول الدعم والإشعارات وسياسات RLS؛ كما يمنح الحسابين الموجودين دور المطوّر دون شرط تأكيد البريد. افحص الاستعلام الختامي حتى يظهر `READY` لكليهما. إذا سبق وشغّلت الملف قبل إنشاء الحسابين، أعد تشغيله.
5. إذا أوقفت **Confirm email** لكن حساب المطوّر أُنشئ سابقًا وهو غير مؤكّد، فإيقاف الخيار لا يؤكد الحساب القديم تلقائيًا. من **Authentication → Users** افتح سجل الحساب واستخدم الإجراء الرسمي لتأكيد البريد/المستخدم. لا تعدّل `auth.users` مباشرة عبر SQL. بعد ذلك جرّب الدخول، مع التأكد من أن `supabase.sql` أعطى الحساب حالة `approved` ودور `developer`. ينطبق ذلك على حسابات Auth القديمة غير المؤكدة؛ ترحيل SQL لا يستطيع تأكيد البريد بدلًا من Auth.
6. بعد ظهور `READY` للحسابين وتأكيد الحسابين الموجودين إن كانا قديمين، أعد تفعيل **Allow new users to sign up** إذا أردت فتح التسجيل العام. لا يوجد تسجيل دخول Google. تنبيه: عند إيقاف التحقق يمكن لأي شخص التسجيل بعنوان بريد لا يملكه؛ لا تستخدم هذا الإعداد إذا كان إثبات ملكية البريد مهمًا.
7. لا تحتاج أوامر `supabase login/init/link` لتشغيل SQL من لوحة التحكم. في **Authentication → URL Configuration** أضف رابط الموقع الفعلي إلى **Site URL** و**Redirect URLs**. رابط استعادة كلمة المرور يستخدم PKCE، لذا افتحه في المتصفح والجهاز نفسيهما اللذين طلبا الاستعادة.

### التسجيل والدخول المباشر

عند تشغيل `supabase.sql`، تصبح الحالة الافتراضية للحساب الجديد `approved`، ويحوّل الملف أيضًا كل الحسابات الموجودة بحالة `pending` إلى نشطة؛ لذلك أعد تشغيل الملف كاملًا بعد هذا التعديل حتى يُطبّق الترحيل. لا توجد موافقة مطوّر مطلوبة: بعد إيقاف **Confirm email** كما في الخطوة 3، يستطيع المستخدم الجديد التسجيل والدخول مباشرة. تأكيد الحسابات القديمة غير المؤكدة يظل إجراءً منفصلًا من **Authentication → Users**، ولا يغيّر SQL بيانات Auth.

### مراجعة RLS في مشروع موجود

قبل استخدام المشروع، راجع السياسات القديمة؛ سياسات PostgreSQL permissive تُجمع بمنطق OR، وقد تُبقي سياسة مخصصة قديمة وصولًا واسعًا. الملف يعيد إنشاء السياسات التي يملكها باسمها، لكنه لا يخمن أسماء السياسات المخصصة الأخرى. استعلم عن السياسات من SQL Editor:

```sql
select schemaname, tablename, policyname, permissive, roles, cmd, qual, with_check
from pg_policies
where schemaname in ('public', 'storage')
order by schemaname, tablename, policyname;
```

احذف أو ضيّق السياسات القديمة فقط بعد التحقق من عدم الحاجة إليها. تم التحقق من اتصال قراءة فقط إلى Auth Settings؛ لم يُنفذ SQL على قاعدة البيانات الحية أو يجرّب تسجيل الدخول.

## الدعم والإشعارات

المستخدم يفتح محادثة خاصة به، ويستطيع المطورون رؤيتها والرد عليها وإغلاقها أو إعادة فتحها. تمنع قاعدة البيانات صاحب الحساب من إرسال رسالة جديدة بعد إغلاق المحادثة. الإشعارات التي يرسلها المطورون تظهر داخل التطبيق فقط. لا يوجد مزود بريد مربوط؛ إرسال البريد الفعلي يحتاج اختيار مزود ووظيفة خادمية، وتخزين مفتاح المزود في **Edge Function Secrets**، لا في `config.js` أو SQL أو واجهة المتصفح.

## الصور وحذف الحساب

تُرفع الصورة إلى حاوية `avatars` الخاصة في Supabase Storage، مع قصرها على الصور المدعومة وبحد أقصى 2 ميجابايت. لحذف الحساب، انسخ `delete-account.ts` إلى مسار Supabase CLI القياسي `supabase/functions/delete-account/index.ts` ثم انشره بـ `supabase functions deploy delete-account`. هذا الجزء فقط يحتاج مجلد وظيفة عند النشر؛ بقية ملفات الموقع تظل في الجذر. لا يسمح المسار لمطور بحذف حساب مطور آخر، وتغيير حالة اعتماد حساب المطور محظور؛ يظل حذف الحساب الذاتي ممكنًا. خزّن `SUPABASE_SERVICE_ROLE_KEY` في **Edge Function Secrets** فقط. لا تتضمن النسخة المحلية بيانات هذا المفتاح ولا يمكن حذف الحساب فعليًا قبل نشر الوظيفة.

## حساب الدخل

تحوّل الحاسبة الراتب الشهري إلى قيمة ساعة وفق `52 ÷ 12` أسبوعًا بالشهر، وأيام العمل وساعات الجدول المسجل. تُحفظ التقديرات اليومية المكتملة تلقائيًا عند الانتقال إلى يوم جديد وتُستعاد الأيام التي فاتت أثناء عدم فتح الموقع ابتداءً من آخر تاريخ مزامنة. لا تُنشأ تقديرات تاريخية قبل تهيئة تاريخ الأساس لتجنب اختلاق دخل سابق. جلسات العمل اليدوية تُقسّم عبر تواريخها عند تجاوز منتصف الليل. هذه أرقام تقديرية وفق جدول العمل، وليست كشوف رواتب أو إثبات حضور أو دفعات.

## حدود بيانات الاتصال والأمان

رابط PostgreSQL الذي يتضمن `[YOUR-DATABASE-PASSWORD]` قالب ناقص، وليس مفتاحًا صالحًا أو مطلوبًا للواجهة أو لتشغيل SQL عبر Dashboard. الرابط والمفتاح العام Publishable المتاحان موجودان في `config.js`. لا تستبدل القالب بكلمة مرور داخل ملفات الموقع؛ أي زائر يستطيع قراءة ملفات الواجهة. عند الحاجة إلى Supabase CLI، أدخل كلمة المرور عند الطلب في بيئة محلية موثوقة ولا تحفظها في المستودع أو ملفات الواجهة. لا تضع مفتاح `service_role` أو أسرار البريد في أي ملف عام.

كلمات المرور التي أُرسلت سابقًا في المحادثة تُعد مكشوفة؛ لا تستخدمها وأعد تعيينها إن استُخدمت. اختر كلمات مرور فريدة وقوية للحسابين.
