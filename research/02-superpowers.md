# Superpowers: planning and testing workflow

## ما الذي يفعله عمليًا؟

العنصر ليس إطار واجهة ولا يفرض React؛ بل هو مكتبة مهارات ومنهج تطوير لوكلاء البرمجة. يعرّف كتالوج السوق إضافة `superpowers` كمكتبة للـTDD وتصحيح الأخطاء وأنماط التعاون، ومصدرها الرسمي هو مستودع `obra/superpowers` [1]. يصف README الخاص بالسوق الإضافة بأنها تتضمن مهارات مجرّبة وأوامر للعصف (`brainstorming`) وكتابة الخطة (`writing-plans`) والتنفيذ (`executing-plans`) [2].

عمليًا، يسير العمل بهذا الترتيب: فهم الهدف والقيود قبل البناء، ثم اعتماد تصميم، ثم خطة تنفيذ صغيرة، ثم تنفيذ كل مهمة مع اختبار، ثم مراجعة والتحقق قبل إعلان الاكتمال. README الرسمي للمستودع الأساسي يصف هذا كسير عمل أساسي: العصف، إنشاء مساحة عمل معزولة عند الحاجة، كتابة الخطة، التنفيذ، TDD، مراجعة الكود، ثم إنهاء الفرع [3].

في مرحلة التخطيط، يجب أن تكون الخطة قابلة للتنفيذ من شخص لم يرَ المشروع: تحديد الملفات الدقيقة، الواجهات والأسماء، الاختبارات التي تثبت كل مهمة، وخطوات تحقق قابلة لإعادة التشغيل. كما يطلب مبدأ YAGNI وDRY وتقسيم العمل إلى مهام صغيرة مستقلة الاختبار [4].

في الاختبار، القاعدة الصريحة هي: **لا كود إنتاجي دون اختبار فاشل أولًا**. دورة العمل هي RED (اكتب اختبارًا يفشل للسبب الصحيح)، ثم GREEN (أقل كود يجعله ينجح)، ثم REFACTOR مع بقاء المجموعة خضراء. ويجب تشغيل المجموعة الكاملة، لا الاختبار الجديد فقط، قبل اعتبار التغيير مكتملًا [5]. عند الفشل، لا يبدأ الحل بالتخمين؛ بل بإعادة الإنتاج، قراءة الخطأ، تتبع تدفق البيانات، صياغة فرضية واحدة، ثم اختبار أصغر تغيير يعالج السبب الجذري [6]. وقبل أي ادعاء بالاكتمال، يلزم دليل تحقق حديث: تشغيل الأمر الكامل وقراءة المخرجات وحصر حالات الفشل [7].

## أفضل ممارسات قابلة للتطبيق على Yourself

- ابدأ كل تغيير في HTML/CSS/JS أو Supabase بوصف سلوكي قصير: ما الذي يراه المستخدم، وما حالة النجاح والفشل، وما الذي **لن** يتغير. ثبّت ضمن القيود أن البنية تبقى HTML/CSS/JS الحالية، وأن الشعار والألوان الحالية لا تُستبدل.
- قبل تعديل الملفات، ارسم خريطة صغيرة للمشروع: صفحة HTML أو المكوّن المسؤول، ملف JS الذي يغيّر السلوك، ملفات CSS ذات الصلة، وطبقة Supabase (استعلامات، سياسات RLS، ورسائل الخطأ). لا تُجرِ إعادة هيكلة شاملة لمجرد تطبيق المنهج.
- اكتب خطة قصيرة لكل ميزة في `docs/` أو مكان توثيق المشروع المعتاد. لكل مهمة اذكر: الملفات، السلوك، الاختبار، أمر التشغيل، والنتيجة المتوقعة. اجعل المهمة قابلة للمراجعة والاختبار منفردة، مثل «التحقق من نموذج التسجيل» بدل «تحسين النماذج». 
- طبّق RED-GREEN-REFACTOR على منطق JavaScript القابل للعزل أولًا: التحقق من المدخلات، تحويل البيانات، حالات التحميل/الخطأ، ومنع الإرسال المكرر. استخدم عدادات ومخرجات حقيقية بدل اختبارات تثبت أن mock استُدعي فقط.
- بالنسبة لتدفقات المتصفح، أضف اختبارات تكامل/واجهة قليلة تغطي المسارات الحرجة: عرض الحالة الفارغة، إرسال نموذج صالح، رفض إدخال غير صالح، وفشل الشبكة مع رسالة مفهومة. استخدم أداة الاختبار الموجودة إن كانت موجودة؛ لا تضف إطارًا جديدًا إلا إذا كانت فائدته واضحة.
- بالنسبة لـSupabase، افصل اختبارين: اختبارات وحدات لتهيئة البيانات والتحقق من المدخلات دون شبكة، واختبارات تكامل لطلب Supabase الفعلي في بيئة محلية/اختبارية. اختبر سياسات RLS بجلستين على الأقل (مستخدم مصرح ومستخدم غير مصرح) وتحقق من شكل الخطأ الذي يحوله الواجهة إلى رسالة آمنة. لا تضع مفاتيح سرية في JavaScript أو الاختبارات.
- عند اكتشاف عطل، سجّل خطوات إعادة الإنتاج والطبقة التي يفشل عندها (DOM، JS، الشبكة، Supabase، أو RLS)، ثم أصلح السبب الجذري باختبار انحدار يفشل قبل الإصلاح. لا تجمع إصلاحات غير مرتبطة في نفس المهمة.
- قبل كل تسليم، شغّل فحصًا آليًا كاملًا، واختبارات الوحدات والتكامل المتاحة، واختبارات المتصفح للمسارات الحرجة. راجع أيضًا يدويًا الشعار والألوان والاستجابة البصرية؛ هذه قيود تصميمية يجب ألا تكسرها اختبارات السلوك.
- اجعل كل مهمة قابلة للتراجع وراجع diff بحثًا عن تغييرات خارج النطاق. احتفظ بقرارات «لماذا هذا الملف/الاختبار؟» في الخطة، لكن لا تنقل آلية Superpowers نفسها إلى التطبيق ولا تحوّل المشروع إلى React.

## الحدود والملاءمة

Superpowers منهج لوكيل البرمجة، وليس بديلًا عن اختيار test runner أو إعداد Supabase أو اختبار توافق المتصفحات. بعض التفاصيل في README تفترض بيئة وكيل تدعم المهارات والأوامر؛ في Yourself يمكن تطبيق المبادئ يدويًا عبر ملفات الخطة وأوامر المشروع الحالية. TDD الصارم قد يكون مبالغًا فيه لملف إعداد أو نموذج بصري سريع؛ يُفضّل تطبيقه على السلوك والبيانات، مع تحقق بصري موجّه للتصميم. كما أن اختبارات Supabase المحلية لا تغني عن مراجعة إعدادات الإنتاج وRLS والهجرات.
