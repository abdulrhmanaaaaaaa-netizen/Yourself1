# تقرير `webapp-testing` لمشروع Yourself

## ما يفعله عمليًا

`webapp-testing` مهارة/عدة تعليمات لاختبار تطبيقات الويب المحلية باستخدام **Playwright** عبر سكربتات Python أصلية. وصفها الرسمي يحدد أربع وظائف عملية: التحقق من وظائف الواجهة، تصحيح سلوك UI، أخذ لقطات شاشة، ومشاهدة سجلات المتصفح. وهي لا تفرض React أو إطارًا بعينه؛ المثال الخاص بالـ HTML الثابت يفتح الملف مباشرة عبر `file://`، بينما المثال الآخر يتعامل مع تطبيق يعمل على `localhost` [1] [2].

المسار المقترح يعتمد على قرارين. إذا كان التطبيق HTML ثابتًا، تُقرأ الصفحة أولًا لاكتشاف المحددات ثم يُكتب اختبار Playwright. وإذا كان ديناميكيًا، فيلزم تشغيل الخادم أو الاستفادة من خادم قائم، ثم الانتظار حتى `networkidle`، وفحص DOM المُصيّر أو أخذ لقطة شاشة، واكتشاف المحددات من الحالة الفعلية، ثم تنفيذ الأفعال والتحقق من النتيجة [1]. السكربت الرسمي `with_server.py` يشغّل خادمًا واحدًا أو عدة خوادم، ينتظر جاهزية المنافذ، يشغّل أمر الاختبار، ثم ينهي الخوادم وينظفها [3].

## أفضل الممارسات القابلة للتطبيق على Yourself

- أبقِ الاختبارات خارج ملفات التطبيق، مثل `tests/e2e/` أو `tests/webapp/`، واستخدم Python وPlaywright؛ لا حاجة لتحويل HTML/CSS/JS إلى React أو تغيير الشعار والألوان.
- للمسارات الثابتة، اختبر صفحة HTML عبر `file://` عند عدم الحاجة إلى خادم. وبما أن Yourself يستخدم Supabase وتفاعلات JavaScript، فالمسارات التي تعتمد على البيانات أو المصادقة ينبغي اختبارها عبر خادم التطوير وبعنوان `http://localhost`.
- قبل فحص عناصر تطبيق Yourself الديناميكية، نفّذ `page.wait_for_load_state('networkidle')`. بعد ذلك افحص DOM المصيّر، الأزرار، الروابط، وحقول الإدخال، بدل الاعتماد على ترتيب العناصر في المصدر؛ هذا يقلل اختبارات هشة عند تغيّر CSS أو ترتيب markup [1] [2].
- استخدم محددات وصفية ومستقرة: `role` أو نص الزر أو `id`/سمات مخصصة مثل `data-testid` عند الحاجة. لا تربط الاختبار بألوان العلامة التجارية أو بنية CSS البصرية إلا عندما يكون المطلوب اختبار المظهر نفسه.
- غطِّ تدفقات المستخدم ذات القيمة: تحميل الصفحة، التنقل، إرسال النماذج، حالات النجاح والفشل، وحالة عدم وجود بيانات. بعد كل فعل مهم، تحقّق من النتيجة المرئية أو من تغيّر DOM، لا تكتفِ بأن أمر النقر لم يرمِ خطأ.
- افصل اختبارات Supabase عن بيانات الإنتاج. استخدم مشروعًا/بيئة اختبار مخصصة أو بيانات seed قابلة لإعادة البناء، ومتغيرات بيئة اختبار، وحسابات اختبار محدودة الصلاحيات. لا تضع مفتاح `service_role` أو أسرار Supabase داخل سكربتات Playwright أو المستودع.
- التقط screenshot للحالة الأولية والنتيجة النهائية عند الحاجة، وسجّل أخطاء `console` أثناء التدفقات المهمة. المثال الرسمي يربط مستمعًا لرسائل console ويحفظها في ملف، وهو مفيد لاكتشاف أخطاء JavaScript التي قد لا تظهر في الواجهة [2].
- استخدم `with_server.py` كغلاف تشغيل عند الحاجة إلى خادم Yourself، بعد تشغيله أولًا مع `--help` كما توصي المهارة. وإذا كان هناك backend منفصل، يمكن تشغيل خادمين معًا وتمرير أمر Playwright بعد جاهزيتهما [1] [3].
- شغّل Chromium في وضع headless وأغلق المتصفح دائمًا بعد الاختبار. أضف انتظارًا قائمًا على حالة العنصر مثل `wait_for_selector` أو انتظارًا قصيرًا فقط عند الضرورة، وتجنب التأخيرات الثابتة الطويلة [1].

## حدود وتكييف ضروري

- هذه المهارة توجّه اختبار المتصفح والتفاعل معه؛ لا تستبدل اختبارات وحدات JavaScript، ولا اختبارات سياسات RLS أو استعلامات Supabase المباشرة. لذلك ينبغي أن تبقى اختبارات قاعدة البيانات والأمن منفصلة، مع استخدام اختبار المتصفح للتحقق من الأثر الذي يراه المستخدم.
- الانتظار حتى `networkidle` مناسب كقاعدة للتطبيقات الديناميكية، لكنه قد لا يستقر في صفحات بها اتصالات طويلة أو polling؛ في هذه الحالات استخدم انتظارًا محددًا لظهور/اختفاء العنصر أو اكتمال حالة الواجهة.
- تشغيل التطبيق عبر `file://` لا يغطي سلوك الخادم، التوجيه، CORS، المصادقة، أو تكامل Supabase. استخدم خادم التطوير لتلك المسارات.
- لقطات الشاشة وسجلات console أدوات تشخيص وليست assertions كاملة؛ يجب أن تحتوي الاختبارات على تحقق صريح من النتائج المتوقعة.
- المستودع يصف هذه المهارات بأنها أمثلة تعليمية وتجريبية، ويوصي باختبارها جيدًا قبل الاعتماد عليها في أعمال حرجة [4]. التقرير لا يغيّر أي ملف من ملفات تطبيق Yourself.
